# Backlog — business-financial-os

Второстепенные находки из ревью `2026-10-19-review.md` — реальные, но не
критичные настолько, чтобы чинить их прямо сейчас вместе с 6 пунктами из
`FIX-PROMPT.md`. Ничего отсюда ещё не исправлено.

## Открыто

### 1. Полноценный merge вместо last-write-wins для владельца бизнеса
`FIX-PROMPT.md` пункт 3 добавляет только проверку версии (owner увидит ошибку
при конфликте вместо тихой потери данных). Правильное долгосрочное решение —
перейти на запись по отдельным ключам и для владельца тоже (как уже сделано
для участников через `update_business_section`), чтобы конкурентные правки в
разные разделы не конфликтовали вообще, а не просто не терялись молча.
Крупная архитектурная работа, не точечный фикс.

### 2. Гостевые бизнесы молча не переносятся в облако, если на аккаунте уже что-то есть
`src/store/authStore.ts`, `migrateGuestDataIfRemoteEmpty()`: перенос
локальных (гостевых) бизнесов в Supabase при входе срабатывает только если в
облаке вообще нет бизнесов. Если у пользователя уже есть хотя бы один
облачный бизнес (вход с другого устройства/ранее уже логинился), локальные
гостевые бизнесы на этом устройстве остаются только в localStorage —
доступны, но никак не предлагаются к переносу и не видны в списке бизнесов
после входа. Данные не удаляются, но для пользователя это выглядит как
"бизнес, который я делал как гость, пропал после входа". Стоит добавить
explicit UI-предложение «перенести локальные бизнесы» вместо тихого условия
"только если облако пустое".

### 3. `generateId()` использует `Math.random()`, не `crypto.randomUUID()`
`src/lib/id.ts` — для `business.id` уже используется `crypto.randomUUID()`
(правильно, это первичный ключ в Supabase), но для вложенных записей
(сотрудники, задачи, цели, товары, статьи расходов и т.д.) — `Math.random()
+ Date.now()`. Коллизия практически исключена при реальных объёмах данных
одного бизнеса, но раз криптографический генератор уже используется в
проекте и доступен везде (браузер + edge functions), логичнее унифицировать
везде на `crypto.randomUUID()` просто для consistency, а не как срочный фикс.

### 4. Нет повторной попытки (retry) при сбое `get_business_view`
Напрямую связано с пунктом 1 из `FIX-PROMPT.md`: после фикса одна неудачная
загрузка бизнеса больше не приведёт к его удалению, но пользователь всё равно
не увидит этот бизнес в текущей сессии, пока не перезагрузит страницу. Стоит
добавить 1-2 автоматических повтора с небольшой задержкой перед тем, как
считать загрузку бизнеса окончательно неудачной.

### 5. Нет UI-индикации, что какой-то бизнес не загрузился
После фикса пункта 1 ошибка загрузки конкретного бизнеса будет только в
`console.error`. Стоит показывать пользователю баннер/тост «Не удалось
загрузить один из бизнесов, попробуйте обновить страницу» — сейчас это
полностью невидимо в UI.

### 6. Прямые confirm() вместо компонента подтверждения
`window.confirm(...)` используется в нескольких местах (`SettingsPage.tsx`,
`TeamAccessPanel.tsx`, `HistoryPage.tsx`) — работает, но не стилизовано под
дизайн-систему проекта и не поддерживает, например, показ деталей (как в
пункте 6 из `FIX-PROMPT.md`, где подтверждение теперь должно перечислять
периоды, которые будут перезаписаны). Стоит сделать единый `ConfirmDialog`
компонент вместо нативного `confirm()`.

### 7. Нет автотестов на сценарий "сломанный JSON в localStorage"
Фикс пункта 4 из `FIX-PROMPT.md` добавляет обработку, но стоит рассмотреть
более широкое покрытие граничных случаев хранилища (квота превышена,
localStorage недоступен в приватном режиме — отчасti уже обработано, но без
тестов).

### 8. `lint` не прогонялся в рамках этого ревью
`npm run lint` (oxlint) не запускался как часть этого прохода — ревью
фокусировалось на поведении, а не на стиле. Стоит прогнать отдельно и
разобрать замечания, если они есть.

## Более крупные темы для отдельного обсуждения (не задача на один присест)

- Реальная офлайн-поддержка / конфликт-резолюшн для мобильного сценария
  (плохая связь на объекте, у кассира/кладовщика).
- Политика ретеншена для `pending_invites`, которые никогда не подтвердятся
  (email так и не зарегистрировался) — таблица растёт бесконечно.
- Аудит-лог изменений командных данных (кто из участников что изменил) —
  сейчас при записи через `update_business_section` нет истории изменений,
  только финальное состояние.
