## 1. [КРИТИЧНО] Не удалять бизнес с сервера, если загрузка хоть одного бизнеса завершилась ошибкой

**Файл:** `src/lib/storage/supabaseFinanceRepository.ts`

- В `load()`: если `get_business_view` вернул ошибку или `null` для какого-то
  `row.id`, зафиксировать это (модульный флаг/множество «не загрузилось в
  этом load()», аналогично существующим `roleByBusinessId`/`domainsByBusinessId`).
- В `save()`: если в последнем `load()` были ошибки — **полностью пропустить**
  блок «удаляем на сервере свои бизнесы, которых больше нет локально»
  (весь `staleIds`-блок). Апсерт существующих/новых владельческих бизнесов
  при этом должен продолжать работать как раньше — ограничение касается
  только деструктивного «cleanup»-шага.
- Не менять поведение для случая без ошибок — существующий тест `deletes rows
  on the server that are no longer present locally (full sync)` должен
  продолжать проходить без изменений.
- Добавить тест: `get_business_view` возвращает ошибку для одного из двух
  бизнесов → следующий `save()` НЕ удаляет этот бизнес со стороны сервера.

## 2. [КРИТИЧНО] Текст и подтверждение «Сбросить все данные» должны честно отражать реальный масштаб действия

**Файл:** `src/pages/SettingsPage.tsx`

- Когда `authStatus === 'authenticated'` (реальный масштаб — весь облачный
  аккаунт, все устройства): текст кнопки и `window.confirm(...)` должны прямо
  говорить, что это удалит **все бизнесы аккаунта из облака навсегда, на всех
  устройствах** — не «в этом браузере».
- Когда пользователь не авторизован (`guest`/локальный режим, масштаб
  действительно «только этот браузер») — оставить текущую формулировку как
  есть, она верна для этого случая.
- Не менять поведение `resetAll()`/`clear()` — только текст/подтверждение,
  показываемые по двум разным веткам `authStatus`.

## 3. [ВЫСОКИЙ] Проверка версии при сохранении владельцем — не затирать чужую параллельную правку молча

**Файл:** `src/lib/storage/supabaseFinanceRepository.ts` (`save()`)

- Перед `upsert` владельческих строк — получить текущий `updated_at` каждой
  из них с сервера (там, где строка уже существует; для новых строк проверка
  не нужна).
- Запоминать `updated_at`, полученный при `load()`, как «последнее известное
  значение» на бизнес (аналогично `roleByBusinessId`).
- Если текущий серверный `updated_at` строки не совпадает с последним
  известным клиенту — **не перезаписывать** эту строку молча. Вернуть/бросить
  понятную ошибку («данные этого бизнеса изменились в другом месте, обновите
  страницу»), чтобы вызывающий код мог её показать, а не терять правку тихо.
- Если строка для `id` ещё не существует на сервере (новый бизнес) — просто
  вставлять, без проверки версии.
- Добавить тест на конфликт: два «параллельных» объекта репозитория сохраняют
  один и тот же бизнес с разным содержимым — второй `save()` должен завершиться
  ошибкой конфликта, а не тихо перезаписать первый.

## 4. [СРЕДНЕ] Не терять повреждённые локальные данные молча

**Файл:** `src/lib/storage/localStorageRepository.ts` (`load()`)

- Если `localStorage.getItem(STORAGE_KEY)` вернул непустую строку, но
  `JSON.parse` упал — НЕ возвращать `null` так, будто данных никогда не было.
  Вместо этого: сохранить сырую строку под отдельным ключом-бэкапом (например
  `bfos:state:v2:corrupted:<Date.now()>`), написать `console.error` с понятным
  текстом, и только после этого вернуть `null`.
- Та же логика для `migrateLegacyState()` при ошибке парсинга `v1`-ключа.
- Не трогать «штатный» путь (валидный JSON или отсутствие ключа) — поведение
  там не меняется.
- Добавить тест: кладём заведомо невалидный JSON под `STORAGE_KEY`, вызываем
  `load()`, ожидаем `null`, но проверяем, что исходная строка доступна под
  резервным ключом (не потеряна).
