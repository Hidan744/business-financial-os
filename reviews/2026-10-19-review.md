# Ревью business-financial-os — 2026-10-19

Ревью сфокусировано на трёх темах, заданных задачей: **потеря данных, сломанные
сценарии, безопасность Supabase**. Это не ревью стиля кода или архитектуры в
целом — те наблюдения, что не тянут на "серьёзно", вынесены в `BACKLOG.md`.

## Методология

Прочитан (не статическим анализом, а построчно) весь storage-слой
(`src/lib/storage/*`), обе SQL-схемы (`supabase/schema.sql`,
`supabase/002_team_access.sql`), edge function `ai-cfo`, `businessStore.ts`
целиком, `authStore.ts`, `RouteGate.tsx` + `teamAccess.ts`, `SettingsPage.tsx`,
`TeamAccessPanel.tsx`, оба импорт-флоу (CSV и Excel history) и их UI, плюс
точечно — `id.ts`, `attachmentStore.ts`, `cfoEngineV2.ts`, `OnboardingPage.tsx`,
`App.tsx` (список роутов) в сверке с `ROUTE_REQUIRED_DOMAINS`.

**Честно о масштабе**: ниже 6 подтверждённых серьёзных проблем, не 15. Каждая
проверена чтением кода (а где было можно — существующими тестами), а не
предположением. Я специально не стал растягивать список до круглого числа
дополнительными мелкими придирками, выданными за "серьёзные" — это было бы
нечестно и бесполезно для приоритизации. Если нужно найти больше — читай
`BACKLOG.md`, там второстепенные находки и более глубокие архитектурные темы
(например, конкурентный доступ), которые стоит разобрать отдельно.

## Подтверждённые серьёзные проблемы

### 1. [КРИТИЧНО, потеря данных] Временная ошибка сети при загрузке → бизнес удаляется с сервера навсегда

**Файл:** `src/lib/storage/supabaseFinanceRepository.ts`, `load()` + `save()`

`load()` вызывает `get_business_view` по каждому бизнесу из `list_my_businesses`.
Если RPC для ОДНОГО бизнеса падает по сети (таймаут, временная недоступность) —
код просто делает `console.error` и `continue`, **полностью пропуская** этот
бизнес из `businesses{}`, без какого-либо флага "это ошибка, а не отсутствие
данных".

Любое следующее действие пользователя вызывает `persist()` → `save()`, которое
считает текущий набор `businesses{}` (без "выпавшего" из-за сетевой ошибки) —
**полным снимком истины**, сравнивает с тем, что реально есть на сервере, и
удаляет "лишние" строки как будто пользователь сам стёр бизнес локально:

```ts
const staleIds = (existingRows ?? []).map((r) => r.id).filter((id) => !ownedIds.has(id))
if (staleIds.length > 0) {
  await supabase.from('businesses').delete().in('id', staleIds)
}
```

Итог: один сетевой сбой при открытии приложения → следующее же действие
пользователя (любая правка) **безвозвратно удаляет бизнес и все его данные**
с сервера. Это не гипотетический сценарий — Supabase RPC может временно упасть
по десятку причин (холодный старт, рейт-лимит, разрыв соединения на мобильном
интернете).

Существующий тест `deletes rows on the server that are no longer present locally
(full sync)` подтверждает, что это поведение — осознанная фича (синхронизация
удалений), а не случайность; проблема в том, что оно не отличает "удалено
пользователем" от "не удалось загрузить".

### 2. [КРИТИЧНО, потеря данных] «Сбросить все данные» обещает «в этом браузере», а на деле стирает весь облачный аккаунт

**Файлы:** `src/pages/SettingsPage.tsx` (текст кнопки и `window.confirm`),
`src/lib/storage/supabaseFinanceRepository.ts` (`clear()`)

Кнопка в «Опасной зоне» и её подтверждение говорят:

> «Удалить все данные всех бизнесов, **сохранённые в этом браузере**, и начать
> заново» / «Удалить все данные всех бизнесов **из этого браузера**? Это
> действие необратимо.»

Формулировка однозначно подразумевает локальный, посл-устройственный масштаб —
как будто это очистка localStorage этого конкретного браузера. Но кнопка не
скрыта для авторизованных пользователей (`hasOtherBusinesses` / блок "Опасная
зона" рендерится всегда), и `resetAll()` вызывает `getActiveRepository().clear()`
— для авторизованного владельца это `SupabaseFinanceRepository.clear()`:

```ts
const { error } = await supabase.from('businesses').delete().eq('owner_id', userData.user.id)
```

Это удаляет **ВСЕ бизнесы пользователя на сервере**, видимые с любого
устройства, а не что-то "в этом браузере". Пользователь, читающий текст кнопки
буквально (разумное чтение — текст специально это обещает), не может
предположить, что нажатие сотрёт данные, которые видны, скажем, с телефона.

### 3. [ВЫСОКИЙ, потеря данных] Владелец сохраняет весь JSON-блок целиком, без проверки версий — конкурентные вкладки/устройства затирают правки друг друга

**Файлы:** `src/lib/storage/supabaseFinanceRepository.ts` (`save()`),
`src/store/businessStore.ts` (`persist()`)

Путь владельца: при каждой правке `persist()` отправляет **весь** `data`
JSONB-блок через `.upsert()`, без каких-либо условий по `updated_at` или
аналогичной оптимистичной блокировки. `schema.sql` уже содержит колонку
`updated_at`, обновляемую триггером — то есть механизм для проверки версий
физически есть, просто не используется при записи.

Сценарий: пользователь открыл приложение на телефоне и на ноутбуке (или просто
в двух вкладках после случайного дубля). На телефоне правит остаток склада, на
ноутбуке в это время правит контакт сотрудника. Чей `save()` отправится вторым
— тот и "победит": весь блок с телефона (без правки сотрудника) перезапишет
блок с ноутбука целиком, и наоборот. Ни один из них не узнает, что чужая правка
исчезла — ошибки нет, просто тихо нет уже той правки при следующей загрузке.

Это архитектурное ограничение (полноценное решение — версии/merge по ключам,
как уже сделано для участников команды через `update_business_section`, но для
владельца пока нет аналога) более затратно чинить полностью, поэтому в рамках
этого прохода применена минимальная, безопасная мера: **проверка версии перед
перезаписью**, превращающая тихую потерю данных в явную, видимую ошибку
("кто-то уже изменил эти данные, перезагрузите страницу"), вместо молчаливого
уничтожения чужой правки. Это не решает конкурентный доступ как таковой (это
крупная архитектурная задача — см. `BACKLOG.md`), но останавливает *тихое*
уничтожение данных.

### 4. [СРЕДНЕ, потеря данных] Повреждённый localStorage неотличим от «данных никогда не было» → следующее сохранение стирает его без возврата

**Файл:** `src/lib/storage/localStorageRepository.ts`, `load()`

```ts
async load(): Promise<MultiBusinessState | null> {
  try {
    const raw = localStorage.getItem(STORAGE_KEY)
    if (raw) return JSON.parse(raw) as MultiBusinessState
    return migrateLegacyState()
  } catch {
    return null
  }
}
```

Если `raw` существует, но `JSON.parse` падает (частичная запись при падении
вкладки/браузера, вмешательство расширения, ручная правка через DevTools) —
метод возвращает `null`, **неотличимо от случая «ключа никогда не было»**.
`businessStore.hydrate()` в ответ на `null` показывает онбординг как для
нового пользователя. Пользователь, скорее всего, просто проходит онбординг
заново — а следующий же `save()` перезаписывает `STORAGE_KEY` новыми данными,
**навсегда стирая** исходную (возможно, лишь частично повреждённую и в
принципе восстановимую вручную) строку.

### 5. [СРЕДНЕ, сломанный сценарий] Изменение доступа участника или его удаление молча не происходит, если RLS это заблокировал — UI не видит разницы

**Файлы:** `src/lib/storage/supabaseFinanceRepository.ts`
(`updateMemberAccess`, `removeMember`), `src/features/team/TeamAccessPanel.tsx`

```ts
async updateMemberAccess(businessId, userId, allowedDomains): Promise<boolean> {
  const { error } = await supabase.from('business_members').update(...).match(...)
  if (error) { ...; return false }
  return true // <- возвращает true, даже если RLS отфильтровал 0 строк
}
```

RLS-политика `"Owners can manage members"` верно не пускает не-владельца
изменить чужое членство — но Postgres/PostgREST в этом случае не возвращает
`error`, он просто не находит строк под политику и обновляет 0 строк. Функция
читает это как успех (`error` пуст → `return true`). В `TeamAccessPanel.tsx`
результат вызова вообще не проверяется (`await supabaseFinanceRepository.
updateMemberAccess(...)` без чтения возврата) — пользователь не получает
сообщения об ошибке, просто видит, что после обновления списка права
"почему-то" не изменились, без объяснения причины.

Это не позволяет обойти авторизацию (RLS отработала верно) — но создаёт
непрозрачный, вводящий в заблуждение сценарий "вроде нажал — вроде ничего не
случилось".

### 6. [СРЕДНЕ, потеря данных / сломанный сценарий] Импорт истории из Excel тихо затирает уже введённые периоды — в отличие от CSV-импорта, без предпросмотра и подтверждения

**Файлы:** `src/pages/HistoryImportPage.tsx`, `src/store/businessStore.ts`
(`importHistoricalRecords`)

CSV-импорт текущего периода (`ImportPanel.tsx`) показывает найденные поля и
требует явного клика «Применить» — осознанное подтверждение. Импорт истории из
Excel (`HistoryImportPage.tsx`) делает наоборот: как только файл распознан,
`importHistoricalRecords(records)` вызывается **немедленно**, без предпросмотра
и без предупреждения о конфликтах:

```ts
importHistoricalRecords: async (records) => {
  await mutateActiveBusiness(get, set, (b) => {
    const importable = records.filter((r) => r.period !== b.financialInputs.period)
    const existing = b.history.filter((h) => !importable.some((r) => r.period === h.period))
    return { ...b, history: [...existing, ...importable].sort(...) }
  })
}
```

Если в файле период совпадает с уже существующей (вручную введённой или ранее
импортированной) записью истории — она **молча заменяется** без какого-либо
предупреждения, что произойдёт замена и чего именно. Опечатка в дате в Excel
("2026-06" вместо "2026-07") тихо перепишет реальные данные другого месяца.

## Область, которую проверил и НЕ нашёл проблем

Для прозрачности — что конкретно проверено и признано корректным, чтобы не
перепроверять это в следующий раз:

- RLS-политики и SECURITY DEFINER функции в `002_team_access.sql`
  (`get_business_view`, `update_business_section`, `create_invite`,
  `list_my_businesses`) — проверка владения/членства на каждом пути
  корректна, не нашёл способа обойти проверку домена или увидеть/записать
  чужой бизнес.
- `RouteGate.tsx` + `isRouteUnlockedForMember` — сверка всех роутов `App.tsx`
  против `ROUTE_REQUIRED_DOMAINS` — расхождений нет, PIN-механизм явно и
  честно ограничен локальным/гостевым режимом.
- `supabase/functions/ai-cfo/index.ts` — секреты только на сервере, функция
  не имеет доступа к БД, узкая поверхность атаки, как и описано в комментарии
  в самом файле.
- `signOut()` → `resetAll()`: порядок вызовов (`setActiveRepository(local)`
  раньше `resetAll()`) корректно гарантирует, что очищается только
  гостевое/локальное хранилище, а не облачные бизнесы — ложная тревога при
  первом чтении, перепроверено внимательно.
- CSV-импорт финансовых показателей (`csvFinancialImport.ts`) — валидация
  чисел, предпросмотр, частичный патч (не трогает отсутствующие в файле
  поля) — корректно.
- `attachmentStore.ts` (IndexedDB) — ограничение (файлы не синхронизируются
  между устройствами) явно задокументировано как принятое, не баг.
- `.env` с публичным `anon key` — закоммичен осознанно и безопасно (см.
  комментарий в файле и RLS-модель), это не секрет в обычном смысле.
